# 无需复制 Cookie：读取已有提交并回传

这是 Manifest V3 浏览器扩展原型。用户在中国站自行登录，扩展只在点击时读取当前已有提交；不导出登录 Cookie、不调用新建提交接口、不安装第三方依赖。支持普通 Chrome / Edge 扩展运行环境，需手动加载一次。

## 当前实现与验收范围

- 扩展文件在 `extensions/leetcode-bridge/`，可以直接加载，不需要 npm 或编译。
- 本地 Web 新增“浏览器回传 · 历史提交”区域与专用接收接口。
- 程序验证包含模拟登录/结果读取脚本，以及真实 HTTP 和 SQLite 的回传测试。
- 2026-10-21 用户在本人浏览器手动验证了一条真实已有提交：原站编译出错，本地显示 `Compile Error`，提交 ID 一致。证据为用户提供的原站和本地页面截图；这不代表真实新建提交或所有判题状态均已验收。

## 操作步骤

### 1. 启动独立的本地接收页面

从项目根目录运行：

```powershell
.\.venv\Scripts\python.exe -m algo_coach.web --demo --data-dir .algo-coach/browser-bridge --port 8767
```

打开 <http://127.0.0.1:8767>。这使用独立数据目录，不占用原有 CLI/Web 学习目录，不需要模型密钥。演示模式仅影响教学回复，接收的浏览器结果单独保存。

也可在正常模型 Web 页面使用，但要重启新版 Web 服务，确保 Python 后端已加载桥接接口。已有服务不会因静态页面更新而自动升级后端。

### 2. 手动加载扩展

Edge 打开 `edge://extensions/`，Chrome 打开 `chrome://extensions/`：

1. 开启“开发人员模式”。
2. 点击“加载解压缩的扩展”。
3. 选择仓库里的 `extensions/leetcode-bridge` 文件夹（不是整个仓库）。
4. 在工具栏扩展菜单找到“AlgoCoach 提交结果桥接”，可以固定以便点击。

本项目不会自动修改你的浏览器配置或读取已有凭据库。扩展仅声明 `activeTab`、`scripting`、`storage` 和 `http://127.0.0.1/*` 主机权限；没有 `cookies`、全站读取或后台自动注入权限。实际权限提示以浏览器为准。

### 3. 连接本地网页

让 `http://127.0.0.1:8767` 成为当前标签页，点击扩展图标，再点击“连接当前本地网页”。无需复制配对码或本地令牌。

配对仅在该本地服务进程内有效，15 分钟内可回传一条结果；连接令牌仅存于扩展 `storage.session`，不放入 LeetCode 页面、不写入本地数据库。相同数据的重试会返回同一回执，不重复写入。读取其他提交时重新连接本地页。

### 4. 在原站登录并打开已有提交

自行在 <https://leetcode.cn> 登录，打开自己已有的一条提交详情。支持以下路径形态：

```text
https://leetcode.cn/submissions/detail/数字ID/
https://leetcode.cn/problems/题目slug/submissions/数字ID/
```

仅停留在题目页或提交列表不够；需要具体提交 ID 的详情页。**无需为了本轮测试新提交代码。**

### 5. 读取并回传

在该详情页点击扩展图标，再点击“读取当前提交并回传”。扩展先在原站同源上下文查询 `userStatus.isSignedIn`，再读取该提交的 `check` 结果；请求由浏览器使用已有登录会话发送，Python 后端不接收登录凭据。

扩展只提取提交 ID、终态、状态码、可选题目内部 ID、运行时间和内存，不回传整份响应、源码、错误原文、账号名或 Cookie。登录未确认、访问拒绝、结果未完成或提交 ID 不匹配时停止，不尝试绕过或新建提交。

扩展提示“已回传”后，回到本地网页下方“浏览器回传 · 历史提交”，点击“刷新回传”，核对提交 ID、结果及原站链接。

## 结果的信任边界

回执来源标记为 `browser_extension_report`，数据库单独存于 `app_browser_receipts`，网页明确标注**未绑定当前代码**。它不是 Python 服务用自身认证直接核验的结果，也没有读取原提交代码后与当前用户代码比较；因此不会改写本地 `Verification`、当前完成程度或模型上下文，不会把旧 AC 自动套到新代码。

配对令牌只限制谁能回传，不是平台对结果的数字签名。未来若接入教学和归档，仍需明确来源及提交代码绑定，不能把扩展报告称作服务器独立认证。

本地接收端只对已配对的精确 `chrome-extension://扩展ID` 开放专用接口的 CORS，普通聊天/文件接口保持原有同源与令牌校验。回传输入有字段白名单和长度限制，不接受原始 Cookie、任意 URL 或任意文件内容。配对过期或 Web 重启后需重新连接。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 扩展说先切到本地网页 | 当前标签页应是 `http://127.0.0.1:端口`，不是原站或扩展管理页；本原型不使用 `localhost` 名称 |
| 本地服务不支持桥接 | 正常退出并重启新版 Python Web 服务，不只刷新静态页面 |
| 提示连接过期或已使用 | 回本地标签页，重新点击扩展“连接当前本地网页” |
| 提示先登录 | 在中国站正常登录并打开详情页后重读，不导出 Cookie |
| 读取失败但网页已登录 | 当前内部接口可能拒绝请求或要求站点验证；停止并在原站处理，不自动绕过 |
| 浏览器询问本地网络/站点访问权限 | 仅在确认是本扩展与本机 AlgoCoach 时按浏览器提示处理；没有权限时回传可能无法完成 |
| 点击回传时学习操作进行中 | 等待当前教学操作结束后重试回传；同一份回执重试不会创建平台提交 |

## 开发验证

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_browser_bridge.py tests/test_web.py -q
node scripts/test_browser_extension.cjs
```

Node 脚本在隔离上下文执行实际注入脚本，模拟原站响应，验证路径、登录、提交 ID、未知状态及字段白名单；它不是浏览器扩展安装或真实原站验收。接口测试覆盖配对、过期、重启、CORS、重复回传、输入校验、持久化与不污染当前学习状态。

本轮结果：22 项 HTTP/后端测试通过（含原有 7 项 Web 回归），10 个注入脚本模拟场景通过，静态/格式/JavaScript 语法和差异检查通过。无头 Edge 自动验收实例的启动被执行审批策略拒绝，仅返回 `blocked by policy`，未提供更详细原因；没有通过其他方式绕过此拒绝。用户随后手动加载扩展并完成一条已有提交的读取回传，原站与本地的提交 ID 和编译错误状态一致；没有自动化安装或新建平台提交。没有重跑完整工程、Docker 或真实模型评估。来源哈希及验证边界见 [证据](evidence/browser-bridge-2026-10-21.json)。

浏览器机制参考：[脚本注入与 activeTab](https://developer.chrome.com/docs/extensions/reference/api/scripting)、[扩展网络权限](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)、[会话存储](https://developer.chrome.com/docs/extensions/reference/api/storage)。这些文档说明扩展机制，不保证中国站内部接口的可用性或第三方接入授权。
